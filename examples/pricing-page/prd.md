# 定价页 PRD

## 0. 文档信息

- 模式：`full`（完整）——本产品此前没有任何公开营销页，定价页是第一个面向站外访客的页面，需要一次把口径讲清
- 状态：in review（评审中，已过一轮 `grill-with-prd`）
- 负责人 / 评审人：产品（本文档）/ 运营（价格口径）/ 研发（静态页实现）
- 关联产物：[clarify.md](clarify.md)（本次仅此一份，`design.md` / `prototype.html` 由后续步骤补齐）

## 1. 执行摘要

本产品目前没有任何公开价格信息，潜在用户要问价只能找销售，转化路径长且不可控。
本期做一个公开定价页：3 档套餐、价格与权益、全功能对比、常见问题，并明确下一步动作。
页面本身不发请求、不做支付，是纯静态页面——**先让价格透明，再谈在线成单**。

同理，**本期页面不区分登录态**：没有后端接口，就无法可靠地知道访客是谁、当前在哪一档。
与其做一个可能标错的「当前套餐」，不如这一版不做（见 §5 范围外）。

## 2. 体验关系

- 产品基线：**无基线**（本项目尚无 `docs/product/` 目录）。定价页是第一个对外页面，
  没有可复用的导航、术语或组件规则；本次所有规则都只是**本功能局部决策**，
  未经二次确认不得当成产品级规范。
- 相关端：C 端（对外营销页）
- 复用基线：无
- 功能局部决策：
  - 套餐分档固定为 3 档：免费 / 专业 / 企业
  - 价格、权益清单由运营提供，产品只负责呈现
  - 行动按钮本期只做跳转，不接支付
- 候选晋升模式：无（首版页面，尚无第二处复用证据）
- 有意偏离：无（无基线可偏离）

## 3. 问题与用户

- 目标角色 / 用户：
  - **未登录访客**——从搜索引擎、社交分享或销售发的链接进来，先看价格再决定要不要留资
  - **已登录免费用户**——已经在用，配额不够时想知道升级要多少钱
- 问题与证据：
  - 竞品均有公开定价页，本产品没有（需求方观察，演示给定）
  - 用户问价只能找销售，销售响应不及时会流失（需求方判断，演示给定）
- 要完成的任务 / 当前行为：
  - 现在：找销售 → 等回复 → 拿到报价单。周期以天计。
  - 期望：打开页面 → 30 秒内知道自己要哪档 → 点下一步。

> **来源口径**：本节「从搜索引擎、社交分享进来」是 §7 R5 的依据；
> 若该入口假设不成立，R5 可降级。

## 4. 战略背景

- 目标 / 为什么是现在：竞品价格已公开，本产品价格不透明正在成为比价环节的劣势。
- 背景：本期先解决「价格可见」，在线成单、试用期、优惠策略都不在本期。

## 5. 范围与方案

### 范围内

- 一页展示 3 档套餐：名称、价格、计费周期、核心权益、行动按钮
- 全功能对比表，按能力分组
- 常见问题（FAQ）
- 移动端可读可用
- 可被搜索引擎收录；分享出去时有标题、描述与预览图
- 关键动作可埋点（曝光、各档按钮点击、对比表与 FAQ 展开）

### 用户流程

1. 用户从顶栏「定价」、首页底部链接，搜索引擎或站外分享进入定价页
2. 从上到下依次看到：页面标题 → 3 档套餐卡片 → 全功能对比表 → 常见问题
3. 在任一档点行动按钮 → 免费档跳注册、专业档跳升级、企业档跳联系销售
4. 已登录用户回到本页时，看到的与访客一致（本期不做登录态区分）

### 范围外

- 在线支付与结算（本期行动按钮只做跳转）
- **登录态区分与「当前套餐」标记**——本期无后端接口，判断不了访客身份与所处档位；
  强行做只能靠前端猜测，标错比不标更伤。待接口就绪后再做
- 已订阅用户的降级入口
- 优惠券、促销码、试用期倒计时
- 月付 / 年付切换与年付折扣
- 多语言与多币种（本期仅人民币）
- 后台套餐配置界面（本期价格写在页面里）

## 6. 成功指标

- 主指标：定价页 → 注册 / 联系销售 的点击转化率。现状无基线（页面尚未存在），
  上线后先采集 2 周建立基线，再谈目标值。
- 护栏指标：销售收到的「问价」咨询占比下降——说明价格确实被页面承接了。
- 数据来源：本期无后端，指标全部依赖 §7 R6 的前端埋点；**R6 不落地则本节无法验证**。

## 7. 需求与验收

> 通用验收（所有需求都适用）：键盘 Tab 可到达页面上每一个可交互元素，焦点可见；
> 页面为纯静态，**无加载态、无错误态**——数据缺失属于发布阻塞问题，不在页面上兜底。

### R1. 浏览套餐与价格

作为访客，我可以在一屏内看全 3 档套餐的名称、价格和核心权益，以便判断自己该选哪档。

验收标准：

- [ ] 3 档套餐同屏并列展示（桌面端），每档含名称、价格、计费周期、权益清单、行动按钮
- [ ] 主推档（专业）在视觉上与其他两档有明确区分
- [ ] 价格按运营提供的口径原样呈现，不做四舍五入或换算
- [ ] 权益清单条目数与运营提供的清单一致，不增不减
- [ ] 企业档若最终采用「联系销售」口径（见 §9），该档不展示具体价格，改为展示「联系销售」；
      同一时刻三档必须口径统一，不得两档标价、一档留空

### R2. 查看全功能对比

作为访客，我可以展开一张全功能对比表，以便逐项确认哪档覆盖我的需求。

验收标准：

- [ ] 对比表按能力分组，每组有组标题
- [ ] 每个能力项在 3 档下都有明确取值（有 / 无 / 具体数值），不用空白表示「无」
- [ ] 移动端下对比表不横向溢出，或提供可横向滚动的容器

### R3. 通过行动按钮进入下一步

作为访客，我可以在选中的档位直接点按钮进入下一步，以便不用再找销售问流程。

验收标准：

- [ ] 免费档 → 注册页；专业档 → 升级流程；企业档 → 联系销售
- [ ] 未登录访客点击专业档按钮 → 先跳登录，登录后回到本页
- [ ] 按钮为真实链接或按钮元素，不得用 `div` 模拟点击

### R4. 查看常见问题

作为访客，我可以在页面底部读到常见问题，以便不用联系销售就能解决基本疑问。

验收标准：

- [ ] 至少覆盖：能否随时取消、超额怎么计费、发票怎么开、数据能否导出
- [ ] 折叠展开可键盘操作，展开状态对读屏可见

### R5. 被搜索引擎收录并可分享预览

作为运营，我希望定价页能被搜索引擎收录、并且分享出去时有像样的预览，以便站外流量能直接落到这一页。

验收标准：

- [ ] 页面有唯一 `<title>` 与 `description`，且描述里包含价格档位信息
- [ ] 有 Open Graph 与 Twitter Card 元信息，含标题、描述、预览图
- [ ] 预览图为固定尺寸的静态图，不依赖用户交互后生成
- [ ] 页面主要文字内容在禁用 JavaScript 时仍可读

### R6. 关键动作可埋点

作为产品，我希望定价页的关键动作都有埋点，以便 §6 的转化率可以被真实计算，而不是靠猜。

验收标准：

- [ ] 埋点覆盖：页面曝光、各档行动按钮点击（带档位标识）、对比表展开、FAQ 条目展开
- [ ] 每个埋点带得清来源渠道（站内 / 搜索引擎 / 站外分享），否则分不出渠道效果
- [ ] 埋点失败不得阻塞页面渲染或按钮跳转

## 8. 依赖、约束与风险

- 依赖：
  - 运营提供的价格与权益清单（未到位，见 §9）
  - 联系销售的落地方式（表单 / 邮箱 / 企微链接）——未定，见 §9
  - 埋点 SDK 或统计脚本——本期新增依赖，需研发确认接入方式
- 约束：本月底上线；本期无后端接口，页面数据静态
- 风险与应对：
  - **价格变更后页面未同步**——本期价格硬编码，改价需重新发版。应对：上线前与运营书面确认一次，并在页面留「价格以销售口径为准」的说明
  - **页面价格与销售口径不一致**——应对：同上
  - **上线时间与价格未到位冲突**——价格是 R1 的输入，价格不定则 R1 无法验收。
    应对：把「价格到位」设为上线阻塞项，而不是页面兜底
