# 需求澄清

在写 PRD **之前**，用采访的方式把一句模糊需求补成可以落笔的完整输入。

它解决的是一个很具体的问题：需求写得不完整时，AI 不会停下来问你，它会按自己的理解去补全——补错了要到测试阶段才暴露。所以缺口必须在落笔前问出来。

## 何时使用

- 需求还停留在口头、聊天记录或一句话描述。
- 需求来源方讲清了「要什么」，但没讲边界在哪。
- 上一版需求返工过，想这次一次问清。

## 不适用

- PRD 已经成文，要挑毛病 → 用 `grill-with-prd`（那是成文之后的对抗式压测）。
- 需求已经完全明确 → 直接用 `prd-write`。
- 上下文已经足够，不需要采访 → 用 `context-to-prd`。

## 输入

- 需求来源方的原话或聊天记录。
- 现有代码库、已有 PRD、`docs/product/` 下的产品体验基线（能查到的不问人）。

## 产物

```text
docs/prd/<feature-name>/
└── clarify.md          # 已知事实 / 角色与权限 / 触发场景 / 范围与不做 / 约束 / 待决问题
```

沿用仓库的标注约定：事实标来源，推断标 `[INFERRED]`，无法确认标 `[UNKNOWN]` 并写明归属人。

## 做法

一次只问一个问题，每个问题都给出推测的默认答案让用户确认或纠正。要问清的五类信息：**目标角色、触发场景、范围、明确不做、已知约束**。

其中「明确不做」是用户最容易漏、也最关键的一条。

## 不做什么

- 不写 PRD 正文。
- 不替用户拍板业务决策。
- 不一次抛出所有问题。
- 不重复问代码库里查得到的事。

## 下一步

把 `clarify.md` 交给 [`prd-write`](../prd-write/) 写新 PRD，或直接进 [`context-to-prd`](../context-to-prd/) 成文。

详细规则见 [SKILL.md](SKILL.md)。
