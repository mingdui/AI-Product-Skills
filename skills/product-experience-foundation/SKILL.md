# 产品体验基线

将项目的可复用产品决策沉淀为版本化文档；保持脚手架的技术通用性，不把某个项目的业务语义、导航或页面内容写入 `frontend/`、`admin/` 等通用模块。

## 定位范围

- 适用于具体产品的首版需求，或已被产品确认需要反复使用的体验模式。
- C 端与 Admin 必须各自维护体验规则；只有品牌、领域术语和跨端业务状态可以放入共享层。
- 不在没有业务依据时预建设计系统，也不因一次功能自动创建全局组件。
- 若当前已有产品基线，只更新被当前需求明确影响的章节。

## 建立或更新基线

1. 确认产品范围。读取首版 PRD、已有页面、产品角色、领域术语和相关前端项目；有多个产品且目标不明确时，要求用户指定产品目录。
2. 在 `docs/product/<project-name>/` 创建或定位产品资产。创建时先阅读 [references/foundation-template.md](references/foundation-template.md)。
3. 记录可证实的事实与明确决策；将合理默认值标为 `[INFERRED]`，将尚未确定的项目列为 `[UNKNOWN]`。
4. 分别建立 `c-end/` 和 `admin/` 基线，只为实际在本项目范围内的端创建文档。
5. 把首批核心流程沉淀为页面模式，而非为未来可能出现的页面预先抽象组件。
6. 对每个候选复用模式记录首次出现位置、复用证据和确认状态。只有用户明确确认，或该模式已被两个已确认功能采用时，才将它升级为产品级模式。

## 推荐结构

```text
docs/product/<project-name>/
├── product-context.md
├── shared/domain-language.md
├── c-end/
│   ├── ux-foundations.md
│   └── patterns.md
├── admin/
│   ├── ux-foundations.md
│   └── patterns.md
└── component-promotion-log.md
```

功能需求仍放在 `docs/prd/<feature-name>/`。功能文档应链接到其依赖的产品基线，并只描述本次变化，不重复全局导航、基础控件和通用状态规则。

## 权威与演进

按以下顺序处理冲突：

1. 仓库架构、安全规则与技术约定。
2. 已确认的产品体验基线。
3. 本次已确认的 PRD 和功能设计规格。
4. 当前项目页面的可见既有模式。
5. 外部网站、截图和通用 UX 建议。

若功能设计需要有意偏离基线，记录偏离原因、影响端和是否应回写基线；不得静默替换品牌、导航、领域术语或核心交互模式。

## 交付与维护

交付时说明：

- 创建或更新的基线文件，以及它们覆盖的产品端。
- 首版已确认的共享模式和仍属功能局部的模式。
- 新增、晋升或拒绝的候选模式及其原因。
- 仍待产品确认的角色、信息架构或领域规则。

后续使用 `pm-frontend-prototype`、`web-design-extractor`、`design-spec-prototyper` 或 `prototype-to-product` 时，先读取对应端的基线；缺少基线时，不得假装它已经存在。
